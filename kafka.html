01. La idea que lo explica todo

Si entiendes esta sola frase, el resto de la presentación se deduce.

🐰 Cola (RabbitMQ)

  • 🗑️
    El mensaje se BORRA cuando alguien lo consume.
  • 📥
    La cola es un buzón: lo que sacas, ya no está.
  • ⏮️
    No puedes volver atrás. Lo consumido se fue.

🌊 Log (Kafka)

  • 📚
    El mensaje SE QUEDA. Nadie vacía nada.
  • 🔖
    Cada consumidor lleva su propio marcador (offset).
  • ⏪
    Puedes rebobinar y volver a leerlo todo.

Leer en Kafka no consume: solo mueve tu marcador.
Es la diferencia entre sacar una carta del buzón y leer una página de un libro.

02. Anatomía de un topic

Un topic es una secuencia ordenada de mensajes. Cada uno tiene una posición fija: su offset.

0clave=5 → {"tipo":"paciente.creado","nombre":"Ana"...}
1clave=6 → {"tipo":"paciente.creado","nombre":"Luis"...}
2clave=5 → {"tipo":"paciente.actualizado","nombre":"Ana M."...} ← historial va aquí
3clave=6 → null   (tombstone: se borró) ← fastapi va aquí
🔑
Clave
Decide la partición. Usamos el id de la entidad, así todos los eventos de un mismo paciente van juntos y en orden.
🔖
Offset
El marcador de cada consumer group. Dos servicios pueden ir por posiciones distintas del mismo topic.
🪦
Tombstone
Un mensaje con cuerpo null. Es la forma canónica de decir "esta clave dejó de existir".

03. Consumer groups: la pieza clave

Con RabbitMQ, cada servicio necesitaba su propia cola para recibir una copia. Si dos compartían cola, el broker les repartía los mensajes en vez de entregárselos a los dos.

📚 salud.pacientes
un solo topic
→
grupo: historial
offset propio
grupo: fastapi
offset propio
📋
Grupos distintos = copias distintas
Los tres servicios leen el mismo topic. Como cada uno tiene su propio grupo, cada uno recibe todos los mensajes. No hacen falta topics separados.
⚖️
Mismo grupo = reparto de carga
Si levantas 3 instancias de un servicio con el mismo grupo, Kafka les reparte las particiones. Ahí está el escalado horizontal, sin configurar nada.

04. La topología del sistema

Dos topics de negocio y sus Dead Letter Topics. Tres particiones cada uno.

TopicEscribeLeenClavePolítica
salud.pacientes🏥 Pacientes📋 Historial · 🐍 FastAPIpacienteIdcompact
salud.historiales📋 Historial🏥 Pacientes · 🐍 FastAPIhistorialIdcompact
salud.*-dltEl error handler(inspección manual)—7 días
🗜️
¿Qué es "compact"?
Kafka conserva para siempre el último mensaje de cada clave. El topic deja de ser solo "cosas que pasaron" y se convierte además en una tabla con el estado actual de cada entidad.
☠️
¿Qué es el DLT?
Si un mensaje falla 3 veces, va al Dead Letter Topic y el offset avanza. Es obligatorio: el offset es un número que avanza en orden, así que un mensaje atascado bloquearía toda la partición.

06. Por qué aquí NO hay RPC

La rama de RabbitMQ implementaba dos patrones: eventos y petición/respuesta. Esta implementa uno solo, y no por pereza.

🐰 El problema con la cola

  • 1
    La cola arranca vacía: solo trae lo que se publique a partir de ahora.
  • 2
    Los pacientes creados antes nunca llegan a la réplica.
  • 3
    Sin un respaldo, se rechazarían historiales de pacientes válidos.
  • 4
    ➜ Hacía falta un RPC para preguntar por lo antiguo.

🌊 Por qué el log lo resuelve

  • 1
    El log está entero y compactado: nada se borró.
  • 2
    Se lee con auto-offset-reset: earliest, desde el offset 0.
  • 3
    Al primer arranque la réplica se construye con toda la historia.
  • 4
    ➜ No hay a quién preguntar: ya lo tienes todo.

Kafka empuja hacia el event-carried state transfer. Se puede forzar un request/reply encima, pero es ir contra su diseño.

09. La demo que solo Kafka permite

Borrar una réplica entera y reconstruirla sola, reproduciendo el log.

# 1. El grupo debe quedar sin miembros para poder mover sus offsets docker stop pacientes-service # 2. BORRAMOS la tabla del read model entera docker exec postgres-salud psql -U admin -d pacientes_db \ -c "truncate table historial_resumen;" # 3. Rebobinamos el consumer group al offset 0 docker exec kafka-salud /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --group pacientes-service \ --topic salud.historiales --reset-offsets --to-earliest --execute # 4. Al arrancar, reproduce todo el log y se rehace sola docker start pacientes-service
✅
Con Kafka
La tabla vuelve a existir con los datos correctos. El log nunca se borró.
❌
Con una cola
Imposible. Los mensajes ya consumidos desaparecieron del broker: no hay nada que reproducir.

10. Que no se pierda nada

Lo que se configuró para que los eventos sean fiables de verdad.

✍️
acks=all + idempotencia
El productor espera confirmación de todas las réplicas sincronizadas y no duplica si reintenta tras un fallo de red.
🔖
Commit manual del offset
El marcador avanza cuando el mensaje se procesó bien, no al recibirlo. Si el proceso muere a mitad, se reentrega.
☠️
Dead Letter Topic
3 intentos con espera creciente; luego al -dlt y a seguir. Un mensaje atascado bloquearía toda la partición.
🛡️
ErrorHandlingDeserializer
Un mensaje corrupto falla ANTES de que exista el listener. Sin este envoltorio, el consumidor entra en bucle infinito.
🔒
Publicar tras el commit
El evento sale después de confirmar en PostgreSQL. En Kafka duele más que en una cola: un evento erróneo queda en el log para siempre.
🔁
Operaciones idempotentes
Kafka garantiza "al menos una vez", nunca "exactamente una vez". Reprocesar debe dar el mismo resultado.

11. RabbitMQ vs Kafka

No es que uno sea mejor. Resuelven problemas distintos.

 🐰 RabbitMQ🌊 Kafka
ModeloCola: el mensaje se borra al consumirloLog: el mensaje se queda
Copia por servicioUna cola por consumidorMismo topic, distinto consumer group
ReprocesarImposibleRebobinar el offset
EnrutadoMuy rico (topic, direct, headers…)Simple: topic + partición por clave
Request/ReplyNatural, bien soportadoSe puede, pero va contra su diseño
Punto fuerteTareas, colas de trabajo, RPCStreaming, event sourcing, alto volumen
Un mensaje atascadoSe rechaza y los demás siguenBloquea su partición: hay que mandarlo al DLT

Regla práctica: si necesitas repartir trabajo, piensa en cola. Si necesitas repartir hechos que varios quieren interpretar a su manera —y quizá reinterpretar mañana—, piensa en log.

La consola web es el mejor apoyo: se ven los topics, las particiones y el lag en vivo.

# El log crudo, tombstones incluidos docker exec kafka-salud \ /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 \ --topic salud.historiales --from-beginning \ --property print.key=true # salida: # 6a7f...c0 -> {"tipo":"historial.creado"...} # 6a7f...c0 -> null <- tombstone

Conclusión

Kafka no es "RabbitMQ pero más rápido".
Es un modelo distinto de qué es un mensaje.

Al no borrar nada, el historial de eventos se vuelve la fuente de la verdad, y cualquier servicio puede reconstruir su estado leyéndolo. Eso elimina la necesidad de preguntarle nada a nadie, pero te obliga a pensar en idempotencia, en particiones y en que un evento erróneo dura para siempre.
