01. La estructura del despliegue

02. Punto de partida: configuración

01-config.yaml separa la configuración de los datos sensibles, y los Deployments los reciben como variables de entorno.

⚙️

ConfigMap: salud-config

Nombres de bases de datos, DNS interno de Eureka y URL de Keycloak.

🔐

Secret: salud-secrets

Usuarios y contraseñas de PostgreSQL, MongoDB, MySQL y Keycloak mediante secretKeyRef.

# El Pod reutiliza la clave sin escribirla en el manifiesto env: - name: POSTGRES_PASSWORD valueFrom: secretKeyRef: name: salud-secrets key: POSTGRES_PASSWORD

03. Persistencia: tres bases de datos

02-databases.yaml crea para cada motor un volumen persistente, un Deployment y un Service DNS interno.

🐘

PostgreSQL

postgres-pvc → postgres-salud:5432. Lo usa pacientes-service.

🍃

MongoDB

mongo-pvc → mongo-salud:27017. Lo usan historial y FastAPI.

🐬

MySQL

mysql-pvc → mysql-salud:3306. Lo consume FastAPI.

Cada motor tiene readinessProbe: no recibe tráfico hasta responder.

04. Identidad y descubrimiento

Keycloak emite identidad y Eureka registra servicios antes de ejecutar la lógica de negocio.

🔑

03-keycloak.yaml

keycloak-salud importa el realm y se expone en NodePort 30080. El realm se monta como ConfigMap.

kubectl create configmap keycloak-realm-config \ --from-file=realm-export.json=keycloak/realm-export.json
🧭

04-eureka.yaml

eureka-server corre en 8761. Los microservicios se registran por su Service DNS.

imagePullPolicy: Never: la imagen debe existir en Minikube.

07. Comunicación entre Pods

Los Services crean DNS internos: usamos nombres estables, no IPs de Pods que cambian.

# Valores reales en los manifiestos SPRING_DATASOURCE_URL=jdbc:postgresql://postgres-salud:5432/pacientes_db SPRING_MONGODB_URI=mongodb://...@mongo-salud:27017/historial_medico_db EUREKA_CLIENT_SERVICEURL_DEFAULTZONE=http://eureka-server:8761/eureka/ JWK_SET_URI=http://keycloak-salud:8080/.../certs
  • ✓Issuer URI: usa localhost:8080, la URL pública del port-forward.
  • ✓JWK Set URI: usa keycloak-salud, alcanzable desde los Pods.

08. Patrón repetido de Kubernetes

Cada aplicación combina Deployment, Service y sondas de salud.

📦

Deployment

Describe réplica, imagen, recursos, puertos y entorno. Si el Pod muere, recupera el estado deseado.

🔗

Service

Selecciona Pods por la etiqueta app y ofrece una dirección estable.

🩺

Probes

readinessProbe controla el tráfico; livenessProbe recupera procesos no saludables.

09. Preparar y aplicar

Construimos las imágenes dentro del Docker de Minikube porque los manifiestos usan imagePullPolicy: Never.

# 1. Clúster e imágenes locales minikube start --cpus=4 --memory=8192 eval $(minikube docker-env) docker build -t eureka-server:latest ./eureka-server docker build -t pacientes-service:latest ./pacientes-service docker build -t historial-medico-service:latest ./historial-medico-service docker build -t pacientes-fastapi-service:latest ./pacientes-fastapi-service docker build -t gateway-service:latest ./gateway-service # 2. Realm y manifiestos kubectl create configmap keycloak-realm-config --from-file=realm-export.json=keycloak/realm-export.json kubectl apply -f k8s/

10. Verificación y diagnóstico

Confirmamos almacenamiento, Pods listos, Services y logs antes de probar la aplicación.

Estado del clúster

kubectl get pods -w kubectl get svc kubectl get pvc

Las PVC deben quedar Bound y los Pods Running/Ready.

Cuando algo falla

kubectl describe pod <pod> kubectl logs deployment/keycloak-salud kubectl logs deployment/gateway-service

Si Keycloak queda en ContainerCreating, revisar keycloak-realm-config.

# Puentes desde la máquina local kubectl port-forward svc/keycloak-salud 8080:8080 kubectl port-forward svc/gateway-service 8090:8090
