01. ¿Qué son los Microservicios?

Un estilo arquitectónico que estructura una aplicación como un conjunto de servicios pequeños, autónomos y desplegables de forma independiente, cada uno ejecutándose en su propio proceso y comunicándose a través de mecanismos ligeros como HTTP/REST.

🧩
Independientes
Cada servicio se desarrolla, despliega y escala de forma autónoma sin afectar a los demás
🔗
Comunicación Ligera
Se comunican via HTTP/REST, mensajería o eventos. Contratos claros entre servicios
🗄️
Base de Datos Propia
Cada servicio gestiona su propia base de datos (polyglot persistence)
🚀
Despliegue Independiente
Se puede actualizar un servicio sin redesplegar toda la aplicación
📐
Dominio Acotado
Cada servicio encapsula una responsabilidad de negocio específica (Bounded Context)
⚡
Escalabilidad Selectiva
Se escala solo el servicio que lo necesita, optimizando recursos

02. ¿Cuándo usar y cuándo NO usar Microservicios?

Los microservicios no son una solución universal. Es crucial entender cuándo aportan valor y cuándo añaden complejidad innecesaria.

✅ Cuándo SÍ usarlos

  • 📈
    Escalabilidad diferenciada — Cuando partes del sistema necesitan escalar independientemente (ej: el servicio de historiales crece más que el de pacientes)
  • 👥
    Equipos grandes — Múltiples equipos trabajando en paralelo, cada uno dueño de un servicio
  • 🔄
    Despliegues frecuentes — Necesidad de actualizar partes del sistema sin afectar el resto
  • 🛡️
    Aislamiento de fallos — Si un servicio falla, los demás siguen funcionando
  • 🗄️
    Tecnologías heterogéneas — Diferentes servicios pueden usar diferentes bases de datos o lenguajes

❌ Cuándo NO usarlos

  • 🏗️
    Proyectos pequeños — Un CRUD simple no justifica la complejidad de múltiples servicios
  • 👤
    Equipos pequeños — Un equipo de 2-3 personas mantiene mejor un monolito
  • 🧪
    MVPs y prototipos — Cuando aún no se conoce bien el dominio, un monolito es más ágil
  • 💰
    Recursos limitados — La infraestructura distribuida cuesta más (DevOps, monitoreo, etc.)
  • 🔗
    Alta cohesión de datos — Cuando todos los datos están muy acoplados y las transacciones son críticas

03. Todo se Conecta con Todo

En esta arquitectura, cada componente tiene un rol específico y todos se interconectan para formar un sistema cohesivo y resiliente.

🔐 → 🌐 → 🏥📋
Keycloak → Gateway → Servicios
Keycloak emite JWT. El Gateway valida el token y enruta. Los servicios verifican el JWT de forma independiente.
📡 ← 🌐🏥📋
Eureka ← Todos los Servicios
Cada servicio se registra en Eureka al arrancar. El Gateway y los servicios consultan Eureka para descubrir a otros.
🏥 ↔ 📋
Pacientes ↔ Historial Médico
Comunicación HTTP directa. Pacientes consulta historiales, Historial valida pacientes. JWT propagado.
🐘 ← 🏥
PostgreSQL ← Pacientes Service
Datos estructurados y transaccionales con JPA/Hibernate. Esquema definido con entidades @Entity.
🍃 ← 📋
MongoDB ← Historial Médico Service
Documentos flexibles con Spring Data MongoDB. Ideal para datos clínicos con estructura variable.
🐬 ← 🐍
MySQL ← Usuarios FastAPI
Registro de usuarios y autenticación propia mediante JWT en Python (SQLAlchemy + aiomysql).
🐳 → 🐘🍃🐬🔐
Docker Compose → Infraestructura
Un solo comando levanta PostgreSQL, MongoDB, MySQL y Keycloak. Todo preconfigurado para desarrollo local.

11. Seguridad con Keycloak

OAuth2 / OpenID Connect con JWT. Cada servicio valida el token de forma independiente.

🏰
Realm: salud-system
Preconfigurado con client y usuarios de prueba
🔑
Client: microservicios-client
Confidencial con Direct Access Grants
👤
Usuarios de Prueba
medico / medico123
admin / admin123

Flujo

  • 1️⃣ Cliente solicita JWT a Keycloak
  • 2️⃣ Servicio valida JWT localmente (JWKS)
  • 3️⃣ JWT se propaga entre servicios
  • 4️⃣ Sin token → 401 Unauthorized
⚠️
Dos esquemas de token (a propósito)
Los servicios Java delegan la identidad en Keycloak (OAuth2/OIDC). FastAPI implementa su propio JWT (HS256) para mostrar el contraste, por eso el Gateway deja pasar /api/consultas/** y es el servicio Python quien lo valida.
SecurityConfig.java
@Configuration @EnableWebSecurity public class SecurityConfig { @Bean public SecurityFilterChain filterChain( HttpSecurity http) { http .csrf(csrf -> csrf.disable()) .sessionManagement(s -> s .sessionCreationPolicy(STATELESS)) .authorizeHttpRequests(auth -> auth .requestMatchers("/actuator/**") .permitAll() .requestMatchers("/api/**") .authenticated()) .oauth2ResourceServer(o -> o.jwt(withDefaults())); return http.build(); } }

12. Guía de Ejecución

Todo el sistema (3 bases de datos + Keycloak + 5 microservicios) está contenerizado: un solo comando lo levanta.

🔑
1. Variables de entorno
cp env.template .env
Completa usuarios y contraseñas vacíos
🐳
2. Levantar todo
docker compose up --build -d
Construye las 5 imágenes y arranca 9 contenedores
📡
3. Verificar Eureka
http://localhost:8761
4 servicios registrados (Gateway, Pacientes, Historial y FastAPI)
🔐
4. Obtener un token
# Keycloak :8080
realms/salud-system/
protocol/openid-connect/token
Usuario medico / medico123
🌐
5. Usar el Gateway
curl localhost:8090/api/pacientes \
-H "Authorization: Bearer $TOKEN"
Toda petición entra por el puerto 8090
☸️
6. Opcional: Kubernetes
kubectl apply -f k8s/
Ver tutorial_kubernetes.md

💡 Para desarrollar un servicio suelto: docker compose up -d postgres mongodb mysql keycloak eureka-server y luego ./gradlew bootRun en ese servicio.
