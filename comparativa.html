OpenFeign vs RabbitMQ vs Kafka

Tres formas de que dos microservicios se hablen. Qué hace cada una, en qué se diferencian de verdad, y cuándo elegir cuál.

OpenFeign · HTTP síncrono RabbitMQ · Cola de mensajes Kafka · Log de eventos

Usa ← → o Space para navegar

01. La pregunta de fondo

Historial necesita saber algo de Pacientes. ¿Le pregunta directamente y espera la respuesta, o le deja un mensaje y sigue con lo suyo? Esa es toda la diferencia entre comunicación síncrona y asíncrona.

📞
Una llamada telefónica
OpenFeign. Marcas, esperas a que contesten y no cuelgas hasta tener la respuesta. Si nadie contesta, no hay conversación.
📬
Un buzón con cartero
RabbitMQ. Dejas la carta; el cartero decide a qué buzón va. El destinatario la lee cuando pueda y, una vez leída, la carta desaparece.
📰
Un periódico archivado
Kafka. Publicas una noticia en un registro que no se borra. Cada lector lleva su propio marcador y puede volver a leer desde cualquier página.
Las tres resuelven el mismo problema (comunicar servicios), pero cambian quién espera a quién, qué pasa si el otro está caído y cuánto tiempo vive el mensaje.

02. Los tres, de un vistazo

Una no es "mejor" que otra: son herramientas de categorías distintas.

OpenFeign
Una librería de Spring Cloud. Escribes una interfaz Java y Feign genera el cliente HTTP por ti. No hay servidor intermedio.
TipoCliente HTTP declarativo
EstiloSíncrono, petición/respuesta
IntermediarioNinguno (usa Eureka)
El mensajeNo existe fuera de la llamada
RabbitMQ
Un message broker: un servidor que recibe mensajes, los enruta a colas y los entrega a quien los consuma.
TipoBroker de colas (AMQP)
EstiloAsíncrono, "push" al consumidor
IntermediarioExchanges + colas
El mensajeSe borra al confirmarse (ack)
Apache Kafka
Una plataforma de streaming: un registro (log) distribuido, ordenado y persistente donde se anexan eventos.
TipoLog de eventos distribuido
EstiloAsíncrono, "pull" del consumidor
IntermediarioTopics + particiones
El mensajeSe conserva (retención)

// Parece local, pero es una llamada HTTP. // Eureka resuelve "pacientes-service" a una IP. PacienteDto p = pacienteClient.obtener(42L); // Si Pacientes está caído, aquí salta // una excepción (FeignException).
En este repo, main hace exactamente esto con RestClient en PacienteClient.java. OpenFeign es la versión declarativa de lo mismo: menos código, idéntico comportamiento en red.

04. OpenFeign: ventajas y desventajas

Lo más simple de las tres opciones. Esa simplicidad sale cara cuando algo falla.

✓ Ventajas

  • ✓
    Respuesta inmediata. Obtienes el dato en el momento, ideal para consultas y validaciones.
  • ✓
    Muy fácil de entender. Es HTTP/REST: se prueba con Postman o curl y se depura como cualquier API.
  • ✓
    Sin infraestructura extra. No hay broker que instalar, vigilar ni escalar.
  • ✓
    Poco código. Una interfaz con anotaciones; integra Eureka, balanceo y Resilience4j.

✕ Desventajas

  • ✕
    Acoplamiento temporal. Si Pacientes está caído, Historial tampoco puede trabajar.
  • ✕
    Fallos en cascada. Un servicio lento bloquea hilos en todos los que lo llaman.
  • ✕
    Punto a punto. El emisor debe conocer a cada receptor; un nuevo interesado obliga a cambiar código.
  • ✕
    Sin memoria. Si la llamada falla, el dato se pierde salvo que tú programes reintentos.

05. RabbitMQ: cómo funciona

El productor no envía a un servicio: envía a un exchange. El exchange decide, por routing key, a qué colas copiar el mensaje. Cada cola entrega a su consumidor y, cuando este confirma (ack), el mensaje se elimina.

@RabbitListener(queues = "historial.eventos.pacientes") void onPaciente(PacienteEvento e) { replica.save(e); // ack al terminar } // si falla → reintento → salud.dlq
RabbitMQ también permite RPC sobre colas (historial.rpc en la rama rabbitmq): pides y esperas respuesta, pero a través del broker en lugar de HTTP.

06. RabbitMQ: ventajas y desventajas

Un broker de propósito general: muy flexible para repartir trabajo, pero el mensaje es "de un solo uso".

✓ Ventajas

  • ✓
    Desacopla en el tiempo. Si Historial está caído, los mensajes esperan en la cola hasta que vuelva.
  • ✓
    Enrutamiento muy rico. Exchanges direct, topic, fanout y headers: decides con precisión quién recibe qué.
  • ✓
    Garantías por mensaje. Ack, reintentos, TTL, prioridades y dead-letter queues listos para usar.
  • ✓
    Baja latencia y fácil de operar. Un solo contenedor y una consola web para ver colas en vivo.

✕ Desventajas

  • ✕
    El mensaje se borra. Una vez consumido no se puede "volver a leer" ni reconstruir el pasado.
  • ✕
    Un consumidor nuevo llega tarde. Solo ve los mensajes publicados después de crear su cola.
  • ✕
    Throughput limitado. Rinde muy bien, pero no está pensado para millones de eventos por segundo.
  • ✕
    Orden frágil. Con varios consumidores o reintentos, el orden de llegada puede alterarse.

07. Kafka: cómo funciona

El productor anexa eventos al final de un topic (dividido en particiones). Nada se borra al leer: cada consumer group guarda su offset (hasta dónde leyó) y avanza a su ritmo.

@KafkaListener(topics = "salud.pacientes", groupId = "historial") void onPaciente(PacienteEvento e) { replica.save(e); // se confirma el offset }
Consumidor nuevo = nuevo group id leyendo desde el offset 0. Recibe toda la historia sin que el productor cambie una sola línea.

08. Kafka: ventajas y desventajas

La más potente de las tres para eventos, y también la que más exige de quien la opera y la programa.

✓ Ventajas

  • ✓
    Replay. Los eventos se conservan: puedes reprocesar, depurar o reconstruir el estado de un servicio.
  • ✓
    Muchos lectores independientes. Cada consumer group lee el mismo topic sin afectar a los demás.
  • ✓
    Throughput enorme. Escala horizontalmente con particiones; millones de eventos por segundo.
  • ✓
    Orden garantizado por clave. Todos los eventos del paciente 42 llegan en el orden en que ocurrieron.

✕ Desventajas

  • ✕
    Más complejo de operar. Brokers, particiones, réplicas, retención y compactación que dimensionar.
  • ✕
    Sin petición/respuesta. No está pensado para "pregunto y espero"; se diseña con réplicas locales.
  • ✕
    Idempotencia obligatoria. Un evento puede llegar más de una vez; el consumidor debe tolerarlo.
  • ✕
    Enrutamiento simple. Solo por topic; no hay exchanges ni reglas finas como en RabbitMQ.

09. La diferencia, en un solo escenario

Registramos un historial médico mientras el servicio que debe recibir la información está caído 5 minutos. ¿Qué pasa con cada opción?

OpenFeign
La llamada HTTP falla con timeout o 503. El usuario ve un error.
Cuando el servicio vuelve, nadie le avisa de lo que pasó.
✕ La operación falla y el dato se pierde.
RabbitMQ
El mensaje se acumula en la cola. El usuario recibe su respuesta al instante.
Al volver, el consumidor procesa la cola y el mensaje se borra.
✓ Nada se pierde. Se entrega una vez.
Kafka
El evento se anexa al log. El usuario recibe su respuesta al instante.
Al volver, el consumidor sigue desde su offset. El evento sigue ahí para cualquier otro.
✓ Nada se pierde. Y se puede releer.
La clave: Feign acopla en el tiempo (ambos vivos a la vez). RabbitMQ desacopla en el tiempo. Kafka desacopla en el tiempo y además guarda la historia.

11. ¿Cuál elijo?

Tres preguntas, en este orden. La primera que respondas con "sí" te da la herramienta.

¿Necesito la respuesta ahora mismo para continuar? (ej. "¿existe el paciente 42?")
SÍ →
OpenFeign+ circuit breaker y timeout
¿Es una tarea u orden que alguien debe hacer una vez, con reglas de enrutamiento? (ej. "envía este correo")
SÍ →
RabbitMQcolas de trabajo, DLQ, prioridades
¿Es un hecho que ya ocurrió y que muchos querrán leer, hoy o en el futuro? (ej. "se creó un historial")
SÍ →
Kafkahistoria, replay, alto volumen
No son excluyentes. Un sistema real suele combinarlas: Feign para consultas puntuales, RabbitMQ para trabajos en segundo plano y Kafka como columna vertebral de eventos.

12. En nuestro sistema de salud

Resolvimos el mismo problema (Historial necesita datos de Pacientes) de tres formas, una por rama.

rama main
Llamada HTTP directa
Historial llama a Pacientes con un cliente REST (PacienteClient) resuelto por Eureka antes de guardar cada historial.
Resultado: simple, pero si Pacientes cae, Historial no puede registrar nada.
rama rabbitmq
Eventos + RPC por colas
Exchange salud.events, colas por servicio, historial.rpc para consultas y salud.dlq para fallos. Java y Python conviven.
Resultado: Historial guarda una réplica local y aguanta caídas de Pacientes.
rama kafka
Réplica desde el log
Topics salud.pacientes y salud.historiales con clave por id, compactación y topics -dlt. Sin RPC.
Resultado: un servicio nuevo reconstruye todo leyendo desde el offset 0.

En una frase

OpenFeign
"Pregúntale y espera." Directo, simple, frágil ante caídas.
RabbitMQ
"Déjale el mensaje." Se entrega una vez y luego desaparece.
Kafka
"Anótalo en el registro." Queda para siempre y cualquiera puede releerlo.
