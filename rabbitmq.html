01. El problema que teníamos

Los microservicios se llamaban entre sí por HTTP, resolviendo la dirección del otro con Eureka. Funciona... hasta que algo falla.

🔗
Acoplamiento temporal
Para crear un historial, Historial tenía que llamar a Pacientes en ese instante. Si Pacientes estaba caído, no se podía registrar nada.
💥
Fallos en cascada
Un servicio lento contagiaba su lentitud a todos los que dependían de él. El error de uno se convertía en el error de todos.
🗺️
Hay que conocerse
Cada servicio necesitaba saber el nombre y la URL del otro. Añadir un consumidor nuevo obligaba a tocar el código del emisor.
⏳
Todo era síncrono
El usuario esperaba a que terminara la cadena completa de llamadas, aunque parte de ese trabajo pudiera hacerse después.

02. ¿Qué es RabbitMQ?

Un broker de mensajería: un intermediario al que le entregas un mensaje y él se encarga de hacerlo llegar. Implementa el protocolo estándar AMQP 0-9-1, así que Java y Python hablan exactamente el mismo idioma.

📮
Exchange
La "oficina de correos". Recibe el mensaje y decide a qué colas va, según su tipo y la routing key.
📥
Queue (cola)
El buzón donde los mensajes esperan. Si el consumidor está caído, esperan ahí sin perderse.
🔀
Binding
La regla que une un exchange con una cola: "mándame todo lo que empiece por paciente.".
🏷️
Routing key
La etiqueta del mensaje (paciente.creado). El exchange la usa para decidir el reparto.

La idea clave: el emisor no le habla al receptor. Le habla al exchange, y ni siquiera sabe cuántos receptores hay.

03. Dos patrones, a propósito

No implementamos uno solo: el proyecto usa los dos para que se pueda comparar el contraste en vivo.

📢 Eventos (asíncrono)

  • 🚀
    Fire-and-forget: publico y sigo. No espero respuesta ni sé quién escucha.
  • 🛡️
    Tolera caídas: si el consumidor está apagado, el mensaje espera en su cola.
  • ➕
    Extensible: añadir un consumidor nuevo no toca el código del emisor.
  • ⚠️
    Precio: consistencia eventual. El dato tarda milisegundos en llegar.

🔄 RPC (petición / respuesta)

  • ⏱️
    Bloqueante: pregunto y espero la respuesta, con un timeout.
  • 🎯
    Dato fresco: te contesta la fuente de la verdad, ahora mismo.
  • 📭
    Sin URLs: el transporte ya es la cola. No hace falta Eureka para esto.
  • ⚠️
    Precio: si nadie atiende la cola, no hay respuesta.

07. El reto: que Java y Python se entiendan

Por defecto, Spring escribe la clase Java del emisor en la cabecera __TypeId__ y exige esa misma clase en el receptor. Eso rompe entre paquetes distintos, y con Python directamente no existe.

// La configuración que lo resuelve JacksonJsonMessageConverter conv = new JacksonJsonMessageConverter(mapper); conv.setTypePrecedence( TypePrecedence.INFERRED);
  • ✔
    INFERRED: deduce el tipo del parámetro del método que recibe, ignorando la cabecera del emisor.
  • ✔
    FAIL_ON_UNKNOWN_PROPERTIES desactivado: el emisor puede mandar campos de más sin romper al receptor.
# El mismo mensaje, visto desde Python { "tipo": "paciente.creado", "pacienteId": 4, "nombre": "Revision", "apellido": "Rabbit", "ocurridoEn": "2026-08-14T21:26:25" }
  • ✔
    El campo tipo repite la routing key dentro del cuerpo: el mensaje se explica solo, sin leer cabeceras AMQP.
  • ✔
    Fechas como texto ISO-8601, no como número, para que Python las entienda.

09. Patrón 2: RPC sobre la cola

Sigue siendo pregunta y respuesta, pero el transporte ya no es HTTP: es la cola. Son tres propiedades de AMQP y nada más.

  • 1
    reply_to — la cola donde quiero la respuesta.
  • 2
    correlation_id — para emparejar respuesta con pregunta, porque pueden llegar varias y desordenadas.
  • 3
    expiration — cuánto vale la pregunta. Si caduca, el broker la descarta.
// Servidor: devolver un valor YA publica la respuesta @RabbitListener(queues = "pacientes.rpc") public ConsultaPacienteRespuesta responder( ConsultaPacienteRequest request) { ... }
# Cliente Python, hecho a mano a propósito await exchange.publish( aio_pika.Message( body=json.dumps({"pacienteId": pid}).encode(), content_type="application/json", correlation_id=correlation_id, reply_to=_cola_respuestas.name, expiration=TIMEOUT_SEGUNDOS, ), routing_key="pacientes.consulta", )

No se usó aio_pika.patterns.RPC porque serializa con pickle y Spring no lo entiende. El protocolo crudo de AMQP sí es común a los dos.

10. Que no se pierda nada

Una cola sin red de seguridad es peor que una llamada HTTP: el fallo se vuelve invisible. Esto es lo que se configuró.

💾
Durabilidad
Exchanges y colas durable, mensajes persistentes y un volumen para el broker: todo sobrevive a un reinicio.
✅
ACK + reintentos
El mensaje se confirma solo si se procesó bien. Si falla, 3 intentos con espera creciente.
☠️
Dead Letter Queue
Agotados los intentos, el mensaje va a salud.dlq en vez de reencolarse para siempre y bloquear la cola.
⏲️
TTL en las peticiones RPC
Si el cliente ya se rindió, la pregunta caduca. Nadie calcula una respuesta que nadie espera.
🔒
Publicar tras el commit
El evento sale después de confirmar en PostgreSQL. Si el commit falla, no se anuncia algo que nunca ocurrió.
🩹
Degradación elegante
Si el RPC no contesta: 503 (servicio caído), nunca 404. Un timeout no es "el dato no existe".

12. Antes y después

Lo que cambió de verdad en la arquitectura del sistema.

AspectoAntes (HTTP + Eureka)Ahora (RabbitMQ)
AcoplamientoCada servicio conocía la URL del otroSolo conocen el nombre de un exchange
Si el otro se caeFalla la operación completaEl mensaje espera en la cola
Añadir un consumidorHay que tocar el emisorBasta con crear una cola y enlazarla
Picos de cargaGolpean directo al servicioLa cola amortigua y regula el ritmo
Clases eliminadasPacienteClient, HistorialMedicoClientSustituidas por publishers y listeners
Rol de EurekaComunicación entre serviciosSolo enrutar desde el Gateway

Lo que NO cambió: la API REST hacia el usuario es la misma. La mensajería es un detalle interno.

🎓

Conclusión

RabbitMQ no hace el sistema más rápido: lo hace más resistente.

Se gana desacoplamiento, tolerancia a fallos y capacidad de crecer sin tocar lo que ya funciona. Se paga con consistencia eventual y una pieza más que operar. Por eso el proyecto conserva los dos patrones: para poder elegir con criterio en cada caso.
